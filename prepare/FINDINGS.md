## 测试 2：文件结构画像 —— ✅ 完成（65 sheet / 11.44 MB）

### 全局数字

| 项目 | 值 |
|---|---|
| sheet 有数据 / 总数 | 65 / 65 |
| 总行元素（`<row>`） | 1,050,740 |
| 总单元格元素（`<c>`） | 2,151,000 |
| 解压后 XML | 133.67 MB |
| 实际文件 | **11.44 MB**（压缩率 8.6%） |

### 结论 1：幽灵行是个例，不是系统性问题

约 104 万行集中在单张 sheet，而该 sheet 实际只有 100 多行、30 来列。
用户确认为**个例**：常规表偶然产生了幽灵行，`dimension` 被撑到约 110 万 × 200 万。

- 不是所有文件都有此问题
- 个别大文件（10 MB 量级）会因此显著变慢（打开需解析百万级空行）
- 清理可行，但**属额外发现，不在本工具范围**
- **设计假设**：工具不负责修复幽灵行，但必须能容忍
  → 任何 sheet 都**不允许整块 `UsedRange` 操作**，只能按声明列操作窄范围

### 结论 2：sheet 保护是强密码，构成真实阻塞

| Sheet | 保护类型 | 能否程序化解除 |
|---|---|---|
| `TOC` | `<sheetProtection>` 无 hashValue / 无 password | ✅ 无密码即可 `Unprotect` |
| `DefineMetadata` | SHA-512 + hashValue + salt + spinCount=100000 | ❌ 需密码 |
| `AE` | 同上 | ❌ 需密码 |
| 其余 sheet | **确认也有保护，且均为 SHA-512 强密码** | ❌ 需密码 |

**这是当前唯一确认的硬性阻塞点。**

### 结论 3：合规上无阻碍

用户确认：**没有 GxP / 21 CFR Part 11 约束**。加锁只是项目组决定。
→ 程序化解除并恢复 sheet 保护**在合规上可接受**。

### 结论 4：文件类型三种，关键词在文件名开头

| 类型 | 文件名前缀 | 说明 |
|---|---|---|
| 1 | `mddt_sdtm`、`mddt_adam` | CDISC SDTM / ADaM |
| 2 | `mddt_vlm` | Value Level Metadata |
| 3 | `mddt_ct` | Controlled Terminology |

- 全部与 **define.xml** 相关
- 三种类型的**锚点假设不同**，需实施前逐类确定
- 类型识别：**按文件名前缀匹配**

### 结论 5：其余 WARN

| WARN | 判断 | 处理 |
|---|---|---|
| `legacy shared workbook`（`fileSharing`） | 与方案冲突 | 必须转普通工作簿；**用户已确认转后所有人可正常打开** |
| `cellXfs is high` | 影响体积但非主要成因 | 忽略 |
| column A key 不唯一 | 原 L3 守卫依赖它 | 由列级声明 + 锚点指纹取代 |

### 其他事实

- TOC 超链接 **7 个，全部内部跳转** → Copy 保真性已实测通过
- 多数文件 ≤ 3 MB，偶有 10 MB 左右
- 实际使用列数远少于 dimension 声明的 500–1000 列

## 测试 3：网络与 Excel 耗时 —— ⚠️ 后期数据作废（服务器降级）

> **重要前提：本测试后期是在服务器严重降级状态下完成的。**
>
> 实测延迟：0 字节文件「创建 + 删除」平均 **3090 ms**，最慢 **14421 ms**。
> 健康 LAN 共享盘应为 **2–10 ms** → 当时慢了 **300–1500 倍**。
>
> 用户自述："现在打开一个空文件夹都需要转 1–2 s，平常在公司没有那么慢。"
> 与实测 `min = 1260 ms` 完全吻合。
>
> → 后期一切数字（341 s 打开、53 s 复制、62 s 上传）都是**降级环境的产物**，
>   不能作为容量基线，但可作为**最坏情况包络**用于确定超时。
>
> **同时确认：不是锁争用。** 测试前残留 `EXCEL.EXE` = 0，锁文件 = 0。
> → 服务器慢本身已能解释全部矛盾，无需引入争用假设。

### 结论 2：`Save()` 是唯一可信的数字，且与大小成正比

| 文件 | SAVE() 区间 | 速率 |
|---|---|---|
| 11.44 MB | 22.6–38.7 s | 0.30–0.51 MB/s |
| 2.92 MB | 5.4–9.0 s | 0.32–0.54 MB/s |

对比参照：
- `Copy-Item` 覆盖 11.44 MB = 8.6–11.9 s（1.0–1.3 MB/s）
- `Move-Item` 重命名 = 0.4 s（不搬数据）
- Excel Save 比裸复制慢 3–4 倍 → **序列化 + 压缩的 CPU 开销，VBA 无法规避**

### 结论 3：其余指标不可重复，全部由服务器降级解释

矛盾点（看似无法调和）：

| 现象 | 违背 |
|---|---|
| 复制 2.92 MB = 53.24 s，而复制 11.44 MB = 8.63 s | 数据少 4 倍却慢 6 倍 |
| 打开 2.92 MB = 341.23 s，打开 11.44 MB = 22–67 s | 同上 |
| 新建 0 字节：1.68 / 2.17 / 5.51 s | 同一操作差 3 倍 |

**统一解释**：`3 s/次延迟 × Excel 打开时的上百次元数据操作 ≈ 300 s`，
与 341 s 吻合。**无需锁争用假设。**

### 结论 4：幽灵行直接拉长 Save 时间

该文件有约 104 万个 `<row>` 元素要序列化。
Save 的 22–39 s 中，相当部分是 Excel 生成 133 MB XML 再压缩的 CPU 开销。

→ 清理幽灵行同时改善：打开（4.83 s → 约 1 s）与提交窗口。

### 结论 5：X: 与 UNC 无性能差异

两者底层是同一条 SMB 连接。SAVE 上 X: 更稳定（38.15/37.38/38.67），
UNC 波动更大（22.59–38.61），区间重叠，不构成结论。

→ 产品仍选 **UNC**（不依赖盘符存在），性能不作为理由。

### 结论 6：手工拖拽 3 s 不代表传输能力（撤回早期推断）

用户确认：把 11.44 MB 拖到**同一共享盘的子文件夹**。
同卷内拖动 = **rename（元数据操作）**，数据不搬，与 `Move-Item` 0.4 s 一致。

→ **不能作为带宽参照。** 唯一有效参照仍是 `Copy-Item` 覆盖 11.44 MB = 8.6–11.9 s。

|---|---|---|
| **宿主实例（推荐）** | **9.409 s** | — |

### 结论 2：内网完全健康，之前“服务器很慢”的结论作废

| 指标 | 内网（本次，VBA） | 外网 WAN（之前，PowerShell） |
|---|---|---|
| open | **3.3 s** | 15–341 s |
| save | **6.8 s** | 22–39 s |
| open+save+close | **9.4 s**（p95 10.6） | 85–137 s |
| 稳定性 | min 8.6 / max 10.6 → **极稳** | 2–4.6 倍波动 |

→ **共享盘本身没问题。之前的怪数字全部是 WAN 链路造成的。**
→ 14 分钟超时不再需要；但保留为安全网。

### 结论 3：PowerShell 确实有额外开销，但不是主因

用户怀疑“是 PowerShell 的问题”。分析：

- PowerShell 访问 COM 是惰性绑定 + `PSObject` 包装，**每属性读写都比 VBA 慢**
- 但对 `Workbooks.Open` / `Save` 这种**整批操作**，COM 调用本身占主导，
  PowerShell 包装开销占比不大
- 所以 341 s → 3.3 s 的差距，**主要是 WAN 而不是 PowerShell**

**验证方法**：在公司内网重跑 `3c-quickdiag.ps1`。
若 PS 测出 open ≈ 3–5 s → PS 无关；若 PS 仍 15 s 而 VBA 3 s → PS 开销坐实。

**对本项目无影响**：产品本身用 VBA，PS 只用于测试。

## 架构结论：架构 B 确定，架构 A 排除

排除「重命名换页」有两个独立理由，任一条都足够：

### 理由 1：速度

每次提交都要把本地副本上传到**新临时文件名** → 命中新建文件路径 → 每次付 106–245 s。

### 理由 2：正确性（更根本）

架构 A 发布的是**整个文件快照**。列级声明模型下：

1. 用户 A 取走并编辑 D 列（耗时数小时）
2. 期间用户 B 提交了 E 列的修改
3. A 提交时把自己的快照整体盖上去 → **B 的 E 列修改全部丢失**

加锁无法解决：锁只保证"同时只有一个人在提交"，
保证不了"他的提交内容已经过时"。

> **必须**是：打开**当前**服务器文件，只改声明列，再存回。
> 即架构 B 是列级声明模型的**必然要求**，不是性能选择。

### 架构 B 的提交流程与窗口

| 阶段 | 实测耗时 |
|---|---|
| 1. 打开服务器文件（读-写） | 健康 8.26 s / 降级 15–341 s |
| 2. 定位并写入声明列 | < 1 s（Copy 25,000 格 = 62 ms） |
| 3. `Save()` 回共享盘 | 健康待测 / 降级 22–39 s |
| 4. `Close()` 释放句柄 | 健康待测 / 降级 12–37 s |

- **健康环境推算提交窗口 ≈ 20–25 s**
- **降级环境最坏 ≈ 7 分钟** → 超时定为 **15 分钟 + 可取消 + 分阶段进度**

### 硬性约束（已由实测确定）

| 约束 | 依据 |
|---|---|
| 提交用 `Save()`，**禁用 `SaveAs`** | Save 22–39 s vs SaveAs 45–210 s |
| 所有暂存文件只在本地 `%LOCALAPPDATA%` | 共享盘新建块吞吐极差 |
| 本地副本放 `%LOCALAPPDATA%`，**绝不放 Documents/Desktop** | 该环境 OneDrive 已重定向（KFM） |
| 配置只存 **UNC**，盘符必须解析成 UNC | 映射盘按用户/会话存在 |
| 提交前做**延迟预检** | 共享盘会阶段性降级 |
| 不依赖盘符、不依赖 `UsedRange` 整块操作 | 幽灵行会让 `UsedRange` 极大 |

## 设计修订：从"表级接管"改为"列级声明 + 锚点校验"

用户提出的规则：

1. 工具**不提供**增删行/列功能
2. 用户除声明 sheet 外，必须**声明要改的列**（列名取自第 1 行）
3. SOP 规定**列名不可修改** → 列名成为结构指纹
4. 列分两类：**Product 列**（仅特定 working group 可改）、**Study 列**（一般用户可改）
5. 写回时除行列定位外，**校验列名与 Product 列**

### 收益

| 原设计风险 | 新设计下 |
|---|---|
| 整表覆盖会覆盖别人其他列的改动 | 只写声明列 → 不同列可并发 |
| 同表多人行级冲突 | 冲突面降到 (sheet, 列集合) |
| key 不唯一无法行对齐 | 用**不可变列组合**作行锚点 |
| 行插入导致写错行 | 逐行校验锚点，不符即拒绝 |
| 幽灵表 `UsedRange` 极大 | 只操作声明列窄范围，不受影响 |

### 锚点可行性（用户实测回答）

- **类型 1（sdtm/adam）大部分 sheet**：Product 列中存在唯一组合 → 可用
- **部分 sheet**：无唯一组合，但模板**只允许加列不允许加行** → 行号即锚点
- **三种类型假设不同** → 实施前逐类确定

## sheet 密码：三种方案

**技术结论：可以。`Worksheet.Unprotect(Password)` 即可。合规无阻碍。**

### 方案 A：用户输入密码

```
取出：逐 sheet 弹窗 → Unprotect → 记录原始保护标志位（密码仅存内存）
提交：Unprotect → 写声明列 → 按原标志位重新 Protect → Save
```

坑：不同 sheet 可能不同密码 / 必须还原所有标志位 / 必须 finally 保证重新保护 /
密码错抛 1004 / 用户不知密码则无法提交 / 密码不得进日志。

### 方案 B：Excel 原生「允许用户编辑区域」（若可改模板，长期最优）

每个可编辑区域有独立密码，表始终保护，权限粒度天然对上 Product/Study 分组。

### 方案 C：约定使用本工具时取消保护（用户倾向）

最简单；补偿手段 = 列级声明校验 + 锚点校验 + 审计日志。

### 关键事实

`.xlsx` 的 sheet 密码**不是加密**，删掉 XML 里的 `<sheetProtection>` 元素即可无密码解锁。
故保护只是**防误操作护栏**，不是安全边界。

**建议先确认**：三种文件的保护是"项目组自己加的"还是"模板自带"？
- 自己加的 → 方案 C
- 模板自带且不能改 → 方案 A
- 模板可改 → 方案 B
